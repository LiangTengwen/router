# H20e 双卡实机验收

2026-11-23，提交 `9fded6187bfc21cdcf549d3b74d9ee7c4b97aa61` 通过会话准入和 Rank 容量两阶段验收。单个 Rust Router 连接两个独立的 vLLM 0.28.0 HTTP 进程，每个进程使用一张 NVIDIA H20-3e。模型为 Qwen3-0.6B，版本 `c1899de289a04d12100db370d81485cdf75e47ca`，Torch 2.13.0，TP=1。两阶段使用同一个 Linux Router，SHA-256 为 `832dd33b99ed1c859e30acf96c17bbfc24dac377b62a0a68daaa4889cdd62cb8`。

| 验收项 | 实机结果 |
|---|---|
| 公平轮转 | A1、A2、B1 依次入队，按 A1、B1、A2 放行。A1 执行期间，排队者新增策略选点计数为 0，队满返回 429 |
| 放行后选缓存 | 两组分别冷启动引擎，重复同一长前缀四次。关闭和开启准入后，vLLM 都报告 0、256、256、256 个缓存 token，Router 都记录了 3 次前缀命中 |
| 负载优先 | 两组在均衡时都复用了 416 个 token。降低负载差阈值、让热 Rank 执行一个长流后，重复请求改发空闲 Rank，两组都记录了一次 `load_imbalance` |
| 容量竞争 | R0 / R1 给入口的配额为 8 / 64 块。两个各需 40 块的大请求只在 R1 先后兑换并执行，最后恢复 8 / 64。每笔认领与真实后端的兑换、结清按尝试号和代际对应 |
| 等待与断连 | R1 占满时，需 1 块的小请求仍在 R0 完成。客户端关闭 SSE 后，R1 可用块仍为 0，收到引擎终止证据才重新放行。另一次等待达 2 秒返回 504，过期请求到达后端 0 次 |
| 认领冲突与重启 | 推荐目标被独立客户端抢先占满，真实认领返回 409。Router 改选另一 Rank，该 Rank 返回 201 并独自处理推理。重启后旧凭证返回 409，新凭证仅能兑换一次 |
| 非法输入 | 显式输出上限加模板超过上下文，以及省略上限但输入已过长的两类请求，均返回 400，新增认领为 0，额度保持 8 / 64 |
| `kv_aware` 与硬容量 | 使用两个 vLLM ZMQ 发布器，先只预热 R0。换新会话后命中 R0 并复用 80 个 token。R0 剩余容量降至 0 后，同一提示转至仍有预算的 R1。三个请求的后端缓存计数为 [0, 80, 0] |

在一次带长流的轮转中，A1、A2、B1 的客户端首 token 时间分别为 117、7899、7789 ms。分别记录客户端首 token 和 Router 入队到放行的时长，可以看出等待来自哪个环节。这组测量只用于验证调度行为。

每台引擎实际配置 256 个 KV 块，每块 16 token，上下文上限 1024 token。8 / 64 是分给 Router 入口的实验配额。每次认领覆盖本轮已知的输入和输出预算，未来轮次重新报价。实验范围为静态 HTTP 混布池和单 Router。
